# Week 5 / Module 3 -- Error Analysis (Track A: Customer Support Tickets)

Domain: same billing-migration help-centre Q&A app as Weeks 3-4 (6 articles, `structure_aware` chunking, hybrid TF-IDF+BM25 retrieval, extractive generation with a hard confidence + grounding gate). That app *is* a customer-support tool, so this week's "20 real support tickets" are 20 real questions run through the actual shipped pipeline -- not a separate synthetic domain.

Full raw traces (question, every retrieved chunk with scores, final answer/refusal, reason) are in [`traces_week5.md`](traces_week5.md), generated by `src/week5_error_analysis.py`. This file is the reading, coding, and ranking done on top of those traces.

## 0. How the sample was drawn (before looking at any output)

A pool of **39** candidate questions was written first, covering all 6 articles and a deliberate mix of realistic ticket phrasing: exact error-code lookups, colloquial paraphrases of the same lookups, vague one-line tickets, a typo, a compound (two-questions-in-one) ticket, a deliberately ambiguous question, and out-of-corpus questions a support inbox genuinely receives. The pool is in `src/week5_error_analysis.py::QUESTION_POOL`.

**20 of the 39 were then chosen by `random.Random(20260822).sample(pool, 20)`** -- a fixed, recorded seed, run once, before any answer was inspected. Sampled: `T34, T32, T08, T09, T36, T01, T17, T21, T20, T26, T07, T03, T15, T16, T30, T31, T19, T39, T11, T12`. Not sampled this round: `T02, T04, T05, T06, T10, T13, T14, T18, T22, T23, T24, T25, T27, T28, T29, T33, T35, T37, T38`. This is what makes the sample fair rather than curated -- the failing questions below were not hand-picked after seeing they fail, and several "boring, obviously fine" questions (T03, T07, T08, T09, T11, T15, T16, T19, T20) are in the sample too and are reported as such.

Pipeline used for every trace: `mode=hybrid`, `strategy=structure_aware`, `k=3` -- the exact defaults `api.py` serves at `POST /ask` with no overrides, i.e. what a real user of this app gets today.

## 4. Fix target for next sprint

**Attacking Group A -- Heading-Only Vocabulary Refusal -- next.**

It's both the most frequent failure in this sample and the one with the clearest, most scoped root cause: `structure_aware_chunk` (chunkers.py) moves every markdown heading out of the chunk body into the `section` metadata field, and both generation-time gates -- `generator._distinctive_coverage` and (for hybrid mode) the TF-IDF-only confidence-gate substitution in `api._for_confidence_gate` -- only ever read the chunk body. The retrieval side is already correct in all three cases (T01, T17, T32); this is purely a "what the grounding check is allowed to see" problem, not a ranking problem, which means the fix is confined to `generator.py`/`api.py` and can't accidentally change what gets retrieved.

**Prediction, written before making the change:** folding each chunk's `section` heading text into what `_distinctive_coverage` (and the confidence-gate's TF-IDF fallback) scores against -- crediting a distinctive word if it appears in the heading *or* the body, not body alone -- should flip T01, T17, and T32 from refusals to correct, cited answers, without changing anything about which chunks get retrieved or in what order. On this same 20-question sample that should raise the correct-outcome rate from 12/20 (60%) to at least 15/20 (75%). It should have **no effect** on T34/T36/T39 (their correct out-of-corpus refusals don't depend on any heading), and it should **not** resolve Group B (T12, T21) or Group C (T26), since neither of those involves heading-only vocabulary -- both stay open problems for the next round of this exercise.
